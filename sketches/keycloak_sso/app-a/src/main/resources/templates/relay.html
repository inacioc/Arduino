Both cards below hit GET /api/reports on Application B. The only difference is whose access token was attached. Application B's /api/reports accepts either app-b-api-reader (machines) or app-b-user (humans), which is why the same endpoint can serve both.

Called with your token, just now

The token oauth2Login stored for you when you signed in is forwarded downstream. Application B therefore knows exactly which human is behind the request — useful for auditing and per-user authorization, and impossible with a machine identity.

Called with Application A's own identity, by the scheduler

Same URL, same instant in the application's life, completely different sub and azp.

How to choose between the two

Application identity (client_credentials) Delegated user identity (relay)
Use when Batch jobs, schedulers, system-to-system sync — work that is not on behalf of anyone The call exists only because a user asked for it, and downstream authorization or auditing depends on which user
Lifetime Independent of any user; renews itself forever Dies with the user's session or refresh token
Downstream authorization Coarse: whatever the service account was granted Exactly the user's own permissions — no privilege escalation
Risk if leaked Full service-account access until the secret is rotated Limited to one user, and short-lived
