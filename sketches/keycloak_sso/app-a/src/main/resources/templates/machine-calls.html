Both calls below run on a scheduler thread. There is no logged-in user to borrow an identity from, so Application A authenticates as itself using the client_credentials grant: it posts its client id and secret to a token endpoint and gets back a token that represents an application. Keycloak does still put a preferred_username in the token — but it is the synthetic service-account-<clientId> user that backs the client, not a person who could ever sit at a login form.

1. Application B — same SSO domain

Credentials issued by Keycloak on :8080. Application A uses the app-a-m2m client, which is a different client from the one humans log in with, and whose service account holds only the app-b-api-reader role.

2. Application C — the other SSO domain

Credentials issued by the second Keycloak on :8090, under the app-a-federated-m2m client. Nothing is shared between the two domains: no keys, no users, no sessions. Application A simply holds two independent sets of credentials. Compare the iss value with the one above.

Why not relay a user token here?

A scheduled job has no user context, so there is no user token to forward. Even if one had been stashed at login, the job would start failing the moment that user logged out or their refresh token expired. Background work needs an identity of its own, which is exactly what a service account is.
